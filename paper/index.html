Abstract #

Vendors, analysts and system integrators describe enterprises populated by thousands of AI agents. This paper argues that the unit to be designed is a different one: not the agent but the Company Brain, a single governed graph of what the enterprise knows, how it works and what it can do — knowledge, procedures and actions, with permissions, provenance and audit on every node — executed by the minimum number of agent archetypes, persistent privilege domains and delegation relationships that separation of duties, isolation, throughput and resilience require, and refined every night by a process that proposes and evaluates improvements from the day's traces and promotes them only under tests, gates and sign-off. The language model is the engine, and it is interchangeable; the brain is the asset that remains the enterprise's own. The reference architecture rests on five pillars: a capability graph with knowledge bases exposed through read-only MCP tools; dynamic tools retrieved per task within a budget; a policy plane that, at every phase declared by an external state machine, materializes the harness profile and the effective privileges; a small runtime team with on-behalf-of (OBO) delegation and no standing data-plane credential per instance; governed evolution that distinguishes descriptive from authoritative nodes. The sources support the components, not a universal topology: the paper separates evidence, architectural inference and hypotheses, illustrates them on a railway risk-assessment case (EU Regulation 402/2013) and refers to a companion document, in preparation, for the experimental protocol that can falsify them [P1].

Keywords: Company Brain · AI agents · capability graph · skills · Model Context Protocol · On-Behalf-Of · policy plane · harness · governed evolution · enterprise governance

1. What a Company Brain is #

The term entered the enterprise vocabulary in 2026 with a Y Combinator request for startups signed by Tom Blomfield [C1]: an enterprise's critical know-how is scattered — in people's heads, in old email threads, in chats, in tickets — and what is needed is a system that extracts it from these fragmented sources, structures it, keeps it current and turns it into a set of executable skills for AI; not a search engine nor a chatbot over documents, but a living map of how the enterprise really works. Those who have taken up the term — AE Studio, Ability.ai, Adapt, Vectorize [C1] — agree on one point: a tool that merely answers is not a brain ("A chatbot over documents is not a company brain", writes Ability.ai; "A graph you can only query is half a brain", Adapt). An enterprise brain knows (the knowledge, with sources and permissions), knows how things are done (the procedures, executed in a repeatable and traceable way), can act (the actions on the systems where the work happens) and is alive: what happens today updates it for tomorrow. Microsoft calls "intelligence layer" — today Microsoft IQ — the context layer that gives agents the enterprise's knowledge [C2]: it is the knowledge ring. The Company Brain described here is the complete operational recipe: the knowledge, and with it the procedures that use it, the agents that execute them, the permissions they do so with, and the nightly analysis cycle that, every day, selects and tests the changes that can improve the whole apparatus.

The title should be taken literally. An enterprise does not need one agent per process, each with its own memory, instructions and credentials: a fleet built that way creates the very fragmentation and governance problems the Company Brain is meant to solve. The number in itself is not the problem: a hundred instances drawing on the same governed graph are not a fleet in this sense; four agents with their own memories and instructions are. An enterprise needs a single brain — a governed graph from which every agent, every assistant and every AI application draws — and the minimum number of actors that execute it. Models improve and get replaced; the brain is the asset that remains the enterprise's own, and the graph is the interface through which the enterprise exposes it: to its own agents today, to other brains tomorrow.

That is the architecture; the rest of the paper describes it component by component, with the sources that support it and the limits it declares; the experimental protocol that can falsify it is in a companion document, in preparation [P1].

1.1 In plain words #

An agent is a program that, given a goal, decides which actions to take — read documents, query systems, write — repeating a cycle of reasoning and action, with permissions delegated to it, until the work is done or it has to stop. The reasoning engine is a language model; everything else (the tools it can call, the instructions it loads, the limits it respects) is what this paper calls the harness.

The model is not the enterprise's brain: it is a market component, replaced and improved from outside. The brain is what the enterprise builds around it (what it knows, how it works, what it can do and with which permissions), and it is what survives a change of model.

Today's commercial offerings promise enterprises thousands of agents, one per process. This paper argues that this draws the boundaries in the wrong place: what must grow into the thousands are the capabilities of the brain (procedures, tools, configurations), collected in a single governed graph — a common logical schema implemented by catalogs federated per trust zone; the types of agent, the persistent privilege domains and the permitted delegations must remain few and legible. Instances can be as many as the load requires, but they receive authorizations limited to the task and the phase: OBO (on-behalf-of) authentication and authorization when the chain supports it, otherwise a confined and declared broker.

The reason is one of governance, not of technology. Every new archetype, persistent domain, trust boundary or delegation relationship adds something to protect, explain and test; every instance also adds context and operational surface, but it must not introduce a new privilege domain. A versioned, signed catalog can be read, compared and rolled back to a previous version, which makes tracing easy — and with it debugging and analysis after an adverse event.

Two questions to ask whoever proposes a fleet of agents: how many security boundaries will I have to govern, and what is the maximum influence that can be exerted through each? And where does the enterprise's knowledge live, and who keeps it current: a shared brain, or the memory of each agent?

The term that most often remains opaque is OBO, and it is also the one the whole security promise rests on. Figure 2 shows it on an example: the same request, "update the hazard record", in an architecture that uses OBO and in one that uses a permanent application credential.

2. The problem: scaling capabilities, not identities #

2.1 The narrative of thousands, millions or billions of agents #

Vendors, analysts and system integrators describe a future in which thousands of agents operate inside every enterprise. The underlying direction (more specialized automation and more tool use) is plausible. The number, however, mixes different units: skills, templates, workflows, instances, persistent identities and running processes. Without an operational definition, "billions of agents" is a commercial metric, not an architectural one.

Box 1. The sources, in their own words

The projections that feed the narrative do not come from marginal analysts. IDC, in a May 2025 study, estimates 1.3 billion AI agents by 2028. Marc Benioff, CEO of Salesforce, declared in November 2024 the goal of one billion agents deployed within a year with Agentforce [F2]. Jensen Huang, CEO of NVIDIA, at GTC in March 2026 described his own company ten years out: 75,000 employees working with 7.5 million agents, one hundred per person [F3]. ServiceNow presents its platform as a "control tower" able to coordinate thousands of agents across CRM, IT, HR and finance (March 2025) [F4]. Microsoft's 2025 Work Trend Index introduces the human-agent ratio as a new business metric, the figure of the agent boss who builds and manages agents, and reports that 82% of leaders intend to use "digital labor" to expand the workforce within 12–18 months [F5]. Accenture, in Technology Vision 2025, foresees multi-agent systems growing to manage processes and entire functions [F6].

The same sources that project the scale also measure the distance from reality: Deloitte, in Tech Trends 2026, reports that only 14% of the organizations surveyed have agentic solutions ready for deployment and 11% use them in production, and cites the Gartner forecast that 33% of enterprise applications will include agentic AI by 2028, against less than 1% today [F7]. Full references in the bibliography.

Adoption data do not prove that fleets are impossible; they only show that autonomy, governance and reliability are still constraints. Today's low adoption does not by itself select the future topology (the shape a fleet of agents takes: hierarchical, linear, swarm, and so on). This is why market statistics should be read not as proof of a topology (neither of fleets nor of the single agent) but as proof of the need for a governable architecture. The metric that matters for an enterprise is not how many agents it has, but how much of its knowledge and know-how sits in one place — current, governed and available to every agent. That is the Company Brain metric, and §3 turns it into architecture.

2.2 What we mean by agent #

The definition of agent is the one in §1.1. What matters here is something else: the word is used for three different things, and confusing them is what produces the numbers of the narrative. This paper keeps them distinct (Table 3, Figure 3). The archetype is the role: it is defined at design time, with a responsibility, the actions it may take and those it may not. The Company Brain uses four, described in §5.1: the Orchestrator decomposes the work and assigns it, without writing; the Reader reads and gathers evidence; the Executor writes to the systems; the Verifier checks, without being able to modify what it checks.

The identity is the way an archetype exists for the enterprise systems: an identity registered in the identity provider with the role's maximum permissions, created in advance and approved by an administrator. There is one per archetype and per security domain (day and night, a tenant, a trust zone): a provisioner creates them in advance from the archetype's blueprint, and no agent can create one for itself while working. The relationship, valid throughout this paper, is archetype → identity per security domain → execution sessions. The instance is the agent at work: a copy of the archetype started for a task or a phase, with its own context, that terminates when the work ends. There are as many instances as the load requires, and none owns permissions of its own: each borrows them for that task and that phase, on behalf of the user, and loses them at the end (§5.4).

Hence the answer to the narrative of thousands. Specialization does not lie in the archetype but in what it receives: the same Reader reads a tender specification in a bid and a hazard record in a railway assessment, because for every task the graph hands it different skills and tools (§3.1). An enterprise may have thousands of processes; the roles that execute them are few. When a vendor counts thousands of agents, it usually counts instances or procedures and presents them as roles. Four archetypes with a thousand instances are governed with four blueprints and one graph. A thousand agents, each with its own identity, permissions and memory, require a thousand principals — with credentials, consents and revocations to inventory — even when the policies come from a few templates and automation reduces the work but not the number of objects; and, if each agent maintains its own procedures, as in the fleet criticized here, a thousand procedural memories to keep aligned. The problem is not the local state of each execution, which should be kept separate: it is procedural knowledge maintained independently, which diverges. The same holds at night: the cycle that improves the catalog (§6.1) is executed by the same four archetypes, with identities of their own, separate from the day's — one more security domain for the same archetypes (§2.3, §6.1).

2.3 When one more archetype is needed #

The goal, then, is not a small number of agents but a small number of roles, identities and delegations, where a delegation is the permission, for one archetype, to activate another (the Orchestrator starting an Executor). The experimental protocol [P1] measures these quantities separately, as components of a vector X = (A, D, I, E): A, the archetypes; D, the identities with persistent permissions; E, the permitted delegations; I, the running instances. The first three must stay at the minimum the work requires; the fourth follows the load. The rule is not "as few as possible" but "the minimum that satisfies the explicit requirements of isolation, accountability and damage containment": the number of identities emerges from those constraints, it is not a goal in itself, and a single identity per archetype may be simpler to inventory but harder to confine than distinct identities per domain (§5.2.1).

A, D, E: the necessary minimum · I: as the load requires

The minimum is not "one". One more archetype is justified when it introduces a real boundary that a skill, a tool or a profile cannot provide: different permissions (whoever executes does not approve), data that must not meet, an independent verification, work to parallelize, a failure to contain. It is not justified when it merely renames a skill. For the same reason a single agent remains the right choice for sequential, low-risk tasks. Whether one more archetype pays for itself is not decided a priori: the metrics of the experimental protocol [P1] decide, by comparing the risk and time saved with the coordination cost it adds.

3. The thesis: one Company Brain, few agents #

In precise form: an enterprise should build a single Company Brain — a governed graph of knowledge, procedures and actions — and minimize the agent archetypes, persistent privilege domains and delegation relationships that execute it, not necessarily the operational instances. An external control plane materializes capabilities bound to the task and the phase; OBO limits the authorization radius only along the chains that support it end to end; confined brokers, isolation, data-flow policies, cumulative budgets and independent assurance limit the other radii. "Few agents" is the editorial shorthand for this sentence, to be read with the definitions of §2.2 and the quantities of §2.3.

The motivation is one of value as well as of governance. Language models improve from generation to generation and get replaced without the enterprise owning them: they are a commodity. What the enterprise owns, and what no vendor can deliver ready-made, is its knowledge and its know-how: the real procedures, the exceptions, who approves what, where the data live. A Company Brain puts them in a graph that any compatible model can execute, once it passes revalidation and with the adaptations revalidation requires (§4.2); a fleet of agents with their own memories and instructions scatters them across a thousand prompts, a thousand memories and a thousand credentials, where they cannot be read, compared or governed. Hence the title: an enterprise does not need thousands of agents; it needs a brain, and the minimum of actors that execute it.

3.1 The five pillars #

The Company Brain rests on five pillars. Together they are the architecture; none of them is a guarantee on its own.

The order is temporal: the graph exists before the task; the bundle is materialized when the task starts, and the policy plane recomputes profile and privileges at every phase; the team executes; evolution works afterwards, on the traces. Figure 4 shows them in action on a task: at the top the day, with the team executing; in the middle the graph, which everyone reads; at the bottom the night, which alone writes to it.

4. What the sources show #

The literature supports the components of the architecture, not a universal topology. This paper separates observed evidence, architectural inference and hypotheses to be tested.

4.1 Skill and tool retrieval #

Graph-of-Skills shows that structural retrieval can outperform indiscriminate loading of the catalog. Version v4 (September 2026) reports, on SkillsBench with GPT-5.2 Codex, an average reward 7.0 absolute points higher (+25.6% relative) than loading the whole library, with 56.7% fewer tokens [2]. The result supports the dependency-aware graph; it does not show that the graph must be consumed by a single agent.

RAG-MCP and MCP-Zero show that retrieving tools dynamically reduces prompt bloat and improves tool selection [3][4]. This result too is topology-agnostic. Moreover, the absolute accuracy of retrieval remains a limit: a critical policy cannot depend exclusively on the probability that the retriever fetches the right node.

4.2 Harness and evolution #

SkillOpt treats the skill as the external state of a frozen model and optimizes it with the discipline of an optimizer [5]. A separate model reads evaluated executions and proposes targeted changes — addition, removal, substitution — within a per-step change budget that decays like a learning rate; a change is accepted only if it strictly improves the score on a selection split, distinct from the test split; rejected changes stay in a buffer the optimizer consults so as not to propose them again; a protected section of the skill changes only through a slow update, at the end of an epoch. The work reports the best or on-par result in all 52 combinations of model, benchmark and harness evaluated, and positive transfer across model scales and across harnesses: a skill optimized in Codex on SpreadsheetBench, used in Claude Code, raises the score from 22.1 to 81.8 (+59.7 points). It optimizes, however, one skill at a time, on curated benchmarks, with neither dependencies nor a library. WikiSkill reports that evolved skills generally transfer well across models and model families, but also documents negative transfer (§5.2.2 and Table 2 of the paper): on the SpreadSheet benchmark the skills evolved by Qwen-3.5-4B lower Gemini-3.5-Flash from 50.5% to 18.1%, while those evolved by Qwen-3.6-27B raise it to 63.4% [6]. The authors attribute this to skills that encode workarounds specific to the model that produced them, instead of general procedures. In the same table other transfers fall below the no-skill score, to a lesser extent: for example Gemma-4-31B on SpreadSheet, from 48.3 to 37.1. The two results must be read together: transfer is often positive but not guaranteed. The catalog is an asset, but it is not independent of the model: every migration requires revalidation on the validation set, and the outcome tells whether the existing skills suffice or whether adaptation and re-optimization are needed. §6.2 adopts its change budget, acceptance by strict improvement and rollback to the best validated version.

HarnessEvolve argues for optimizing the whole harness and uses a pipeline with independent modules for execution, evaluation, optimization and gating [7]. The source itself describes a multi-agent architecture. It is therefore evidence in favor of governed evolution, not of the "single agent" thesis. The line of work on agent self-evolution — libraries of learned skills (Voyager [14]), automatic generation of workflows and of agentic systems (AFlow [15], ADAS [16]), reasoning memories (ReasoningBank [17]) — shows what an improvement cycle can produce; none of these sources includes the gates, the sign-offs and the rollback that §6 requires.

4.3 MAST: what it says and what it does not #

MAST is a taxonomy of the failures of multi-agent systems and a roadmap for improving them [1]. In version v3 the "context loss" category accounts for 2.8% of the observed failure modes: that is the prevalence of a category, not a measure of the causal importance of topology; most failures concern reasoning-action mismatch, derailment, ignored information, coordination, and wrong or superficial verification. The authors also acknowledge the advantages of parallelization, decomposition and context isolation. The defensible conclusion is "the topology must be chosen and tested", not "multi-agent systems must be abolished".

4.4 What harnesses already provide #

Part of the architecture need not be built: it already exists in mature agentic harnesses — Claude Code and Cowork, the Agent SDK, Microsoft Agent Framework, graph orchestrators. Subagents with restricted tool lists declared in a definition file, skills loaded by progressive disclosure, tools retrieved on demand, hooks before and after every call, confirmation for irreversible actions, isolated workspaces, persistent memory and the proposal of new skills from recurring procedures: these are useful primitives, and the paper assumes them as substrate. But coverage, semantics and enforcement vary by product, version, tool class and delegation path, and every property must be verified case by case: in some harnesses a subagent may have MCP servers of its own that the caller does not possess, or inherit all tools unless explicitly restricted [19]; tool guardrails do not necessarily cover handoffs, hosted MCP or agent-as-tool [20]; and "observed content is data, not instruction" is a security objective, not a guaranteed property — a case is documented in which a malicious file induced a harness to read other files and exfiltrate them to an allowed domain, with sandbox and allowlist working exactly as configured [13]. The table distinguishes what the harness provides, what it provides in weak form — as an in-process control, not as a barrier — and what it does not provide at all.

The boundary that matters is the one between in-process control and external barrier. A subagent's restrictions are an excellent operational control, but they live in a product's configuration: change the harness and they are lost, and an auditor will not accept them as the only proof of separation of duties. What lives in the identity provider, in the policy plane and in the signed catalog survives a change of harness as it survives a change of model. The paper's thesis is therefore "the harness is the substrate": the agent loop, subagents, skills and hooks need not be rewritten; they must be configured and, in their barrier function, replaced by an external control.

4.5 Related work: per-phase harness and long horizons #

No published work tests the composition proposed here — the harness profile as a versioned node, recomputed at the phase boundary by an external state machine — but its components have been tested separately, with results that support some and scale down others. The paper uses them to distinguish what per-phase partitioning promises for security from what it promises for quality on long tasks.

Cutting the context at the boundary. Sinha et al. show that on long tasks the model degrades not only with context length but through self-conditioning: conditioning on its own previous errors reduces accuracy at turn 100, and scaling the model does not mitigate it; sliding windows over the context, and the reasoning models studied, which do not self-condition, attenuate it [21]. The horizon residual protocol separates the error that compounds by pure probability from the error induced by the trajectory, and cites the case in which inheriting self-produced state lowers bug-fix accuracy from 58.9% to 36.5% [22]. Anthropic's harnesses for long tasks followed the same road and then partly abandoned it: in November 2025 an initializer agent and a coding agent handed the work over between sessions with context resets and a progress file [23]; in March 2026 the three-role harness — planner, generator and evaluator — replaces compaction with structured handoff artifacts, but the authors state that they removed context resets with Opus 4.5 and simplified the harness further with Opus 4.6, because the model no longer needed them [30]. The phase boundary of §5.3 is where this cut happens: if the quality gain exists, it comes from there, and it depends on model and task.

Prompts and tools per state. StateFlow is the most direct precedent: a state machine in which every state has its own prompt, tools and actions, with +13% and +28% success over ReAct on InterCode SQL and ALFWorld and 5× and 3× lower cost [24]. The tasks are short and the transitions are decided by heuristics or by the model itself; this paper's variant, with the transition taken away from the model, has not been measured on long horizons.

Model per phase. AgentRouter routes every step to one of four model tiers and reports a 72% cost reduction with less than 3% completion degradation [25]. The Replay Gap warns, however, that switching models mid-trajectory rewrites 61–94% of the subsequent actions, that replay-based evaluations of logs run over states that do not exist — for early switches only 3–8% of replayed states remain valid — and proposes, as hypotheses it declares unconfirmed, to switch to a lower tier late and to escalate hard cases early [26]. The paper draws from it a methodological constraint — evaluate the hypothesis live or with branching, not by replay — and a conservative design choice, which is not a necessary consequence of the source: the model changes at the phase boundary, after a clean handoff, never per step inside a phase.

Privilege per phase. Progent formalizes monotonic confinement: the tool policy can be tightened automatically during execution and loosened only with explicit approval, with attack reduction on AgentDojo and ASB at preserved utility [27]. The Company Brain adopts a different model, which does not claim the same formal guarantee: the conditional activation of pre-authorized privileges. The task envelope — the set of permissions authorized at start in the task decision record, within the manifest's maxima — remains unchanged until a new explicit authorization produces a new version of the task decision record; every phase activates a portion of it, possibly wider than the previous one. What remains of Progent is the part the two models share: whatever leaves the envelope requires explicit approval, never a decision by the model (§5.3.1). This is the part of §5.3 that stands on its own: it is justified by security and auditability even if the quality gain were nil.

Separation of control and data. CaMeL [31] defends against prompt injection by construction: a privileged model plans without seeing the data, a quarantined model reads them without being able to act, and every value carries capabilities that forbid unauthorized flows, with provable security on AgentDojo. It is the closest precedent to the Reader/Executor pair and to the requirement "content treated as data" (§5.6), with a difference of scale: CaMeL does it inside a program; here it is done by roles with identities, signed artifacts and an external policy plane.

Harness descriptors. Ruflo MetaHarness treats the harness as an object measurable from outside: a score on five dimensions, a categorical genome and a persisted fingerprint to detect drift between one audit and the next [28]. Its unit is the whole runtime at build time, not the phase at runtime, and its factory operation (mint) multiplies harnesses as deployment units — the opposite of what this paper proposes. The paper borrows from it the genome vocabulary for node metadata (§5.2) and drift as a metric (§6.2; [P1]), not the mechanism.

Where partitioning remains superstructure: when the task does not decompose into stages with verifiable checkpoints — the residual protocol expresses this in terms of exposed work and dependency depth [22] —, when the phases share the same context with neither reset nor artifact, and to the extent that reasoning models erode the advantage of the cut. The governance advantage remains in any case. The experimental protocol [P1] states the quality part as a falsifiable hypothesis (H7).

4.6 Why not one agent, why not thousands #

The thesis of §3 sets a minimum and a maximum; the sources of this chapter motivate both. The minimum is not one. A single agent that reads, writes and verifies with a single identity would be, on paper, the simplest to govern — one context, one credential, one audit — and yet, precisely because it minimizes the quantities of §2.3, it maximizes the concentration of authority: its influence (§5.5) coincides with the whole process. A verifier that can modify what it evaluates is not a verifier: MAST places wrong or superficial verification among the most frequent failure classes (§4.3), and separation of duties is the structural remedy, alongside deterministic rubrics and human gates; it is not entrusted to a prompt. A context that has read untrusted content — a tender specification, an email, a web page — and that in the same turn can write to systems is the path of prompt injection (§7.5): the Reader that does not write to systems and the Executor that does not read the outside are two archetypes because they are two trust zones. An identity with all the permissions of the process is the maximum privilege domain: per-phase OBO limits the radius only if, for every phase, there is a session to give a different capability to, and a broker that enforces for every session the constraints of its capability (§5.4). To these three security reasons three operational ones are added: throughput, because a single runtime is a bottleneck and a single point of failure [8], and its replicas are no longer "a single context"; data boundaries, because residency, classification and need-to-know may impose separate instances even under the same control plane; model specialization, because a phase may be better served by a different model, at the price of a separate validation of the skills (§4.5). None of these reasons calls for one more agent per task: they call for the four archetypes to remain distinct.

The maximum is not thousands. Multiplying persistent identities, autonomous contexts and local goals increases coordination, observability and administrative surface. Two costs must be kept distinct. Execution costs (concurrent states and race conditions, handoffs and information loss, fan-out, audit volume, common-mode and cascading failures) grow with executions and interactions, hence also with a thousand instances of four archetypes: these are the failure classes that MAST observes in coordination and verification, not in topology as such, and they are governed with budgets, depth and fan-out (§5.5). Governance costs (the delegation call graph and its transitive closure, the reachable combinations of capabilities, the principals to inventory and revoke, the policies and procedures to keep aligned) grow with identities, domains and delegations. The strong thesis is about the latter: reduce the duplication and the independent management of policies and procedures. The graph makes governance uniform; it does not make N irrelevant. The thesis does not forbid fleets: it requires every additional identity to demonstrate a net benefit, and Box 2 says when creating one is legitimate. Where a skill or a profile suffices, creating an agent is over-architecture. Finally there is a knowledge cost: a thousand agents with their own memory and instructions are a thousand partial brains, which recreate in the fleet the fragmentation — in heads, in threads, in tickets — that the Company Brain is born to escape.

Box 2. Design rule

Create a new agent only when at least one among privilege, trust zone, data, independence, parallelism or resilience cannot be obtained more simply with a skill, a tool or a profile.

5. Reference architecture #

The architecture of the Company Brain separates five responsibilities: capability graph (with the knowledge bases its tools expose), policy plane, orchestration, agent runtime and assurance. The graph describes; the policy plane authorizes; the agents decide within boundaries enforced from outside. Orchestration and agent runtime are provided by the harness (§4.4); capability graph, knowledge bases, policy plane and assurance are the components to add, and this section describes mainly those.

Two planes, not one. The policy plane of this paper is the decision point of the Company Brain, and must be distinguished from the enforcement plane the platform provides. The first reads the graph: the phase manifest, the bundle retrieved for the role, the Orchestrator's delegation capability, the constraints on the arguments of every call, the cumulative budget of the trajectory; it computes the intersection of §5.4 and issues a decision record at two levels: a task-level one, at start, which fixes the envelope of this execution (§5.3.1); and a call-level one, which binds every call to task, phase and catalog version. The second is the management control plane — agent registry, identities and blueprints, admin consent, conditional access, data protection and threat detection — and sets the outer boundary within which the first works: the policy plane materializes only tools, servers and scopes that the control plane has already approved, and does not replace it. At Microsoft the control plane is Agent 365 with Entra Agent ID, Purview and Defender; the Dynamic Permissions announced in October 2026 — no initial authority, only what the approved task requires, for as long as it requires it, with human approval for high-impact actions [29] — bring into the product the mechanics of issuing and expiring permissions that §5.4 describes. What remains with the Company Brain, and has no platform equivalent in the products cited as of October 22, 2026, is the input to those mechanisms: what a task requires in this phase is known to the graph, not to the identity provider. In the vocabulary of access control [32], the policy plane is a policy decision point, and gateway and broker are policy enforcement points: the separation between decision and enforcement is well established, and NIST describes it in federated form too; the specific contribution lies in the input to the decision — the phase manifest, the bundle and the delegation — which comes from the graph.

5.1 The small runtime team #

The roles are logical: in low-risk tasks Reader and Executor may coincide; in regulated tasks they must remain separate. "Read-only", for the Reader, has a precise perimeter: it modifies neither source systems nor approved artifacts; it may produce new intermediate artifacts in the namespace assigned to the task, through the path the harness provides, as with the excerpts of the preliminary investigation of §7.2 and the candidate wiki of Dreaming. Separation of duties concerns the modifiable resources, not the literal absence of any write. "Few" does not necessarily mean four permanent processes: it means instantiating only the boundaries the task class requires.

Four levels must be kept distinct. The roles are a closed vocabulary, defined at design time. Persistent identities are registered in advance in the identity provider: one blueprint per archetype, with maximum scopes and admin consent, from which a provisioner creates the identities per security domain [11]. The instances are dynamic: how many to activate, and in which phase, is decided by the Orchestrator within policy. Every instance is a session: two Readers are actors distinguishable in the logs and separately revocable through the session identifier, the token the session uses and the decision record that authorized it — not through an identity of their own. A short-lived child identity per instance, derived from the role's blueprint and free of individually administered grants, would be the strongest property, but the reference identity provider of this paper does not offer it: Entra Agent ID creates agent identities from the blueprint with explicit provisioning and registers them as administered directory objects, with equally explicit deprovisioning [11]. Even if it became available one day, it would limit the radius at the credential level, but it would not by itself demonstrate isolation of a compromise: broker, runtime, queues, caches, artifact store, policy plane and the blueprint's federated credential may remain shared. Isolation between instances therefore requires separate controls on compute, memory, data and control plane. The bundle — skills, tools and profile retrieved from the graph — is what varies per task: specialization comes from the bundle, identity from the role. The mapping between blueprint, session and job duration is a reference pattern to verify for every IdP and harness, not a universal primitive.

Fault domain of verification. Logical separation of roles does not guarantee independence. Orchestrator, Executor and Verifier may share model, derived system prompt, capability graph, runtime, contaminated artifacts, validation set and control plane, and in that case the Verifier may confirm exactly the Executor's error: the taxonomy of multi-agent failures observes that the presence of a verifier is not a solution in itself and that many verifications remain superficial [1]. The independence that matters requires at least some different fault domains: a distinct verification model or prompt, deterministic rubrics alongside the model's judgment, immutable artifacts, a verification policy separate from the execution policy and, for critical classes, a different human or organizational principal. Blocking power, finally, is a power: it must be limited in time and effects, with mandatory escalation to a human when it exceeds the SLA. Expiry is not approval: for critical classes the outcome remains fail-closed, in a human queue.

Box 3. Objection: what about tasks that do not fit?

If the roles are fixed, at runtime one always ends up with those and only those, for tasks of any complexity. That is intended. Complexity is absorbed by the three dynamic dimensions — how many instances, with which bundle, under which per-phase profile — not by the number of agent types: a simple investigation has one Reader, a complex change has six in parallel, and the same Reader receives the HAZOP bundle in a railway task and the contract-analysis bundle in a procurement task. When a platform's registry shows twelve agents for one process, it is often showing twelve bundles or twelve phases of one and the same privilege domain: the registry should be read by privilege domains, not by entries. If a task class emerges that requires a boundary no role covers — a different trust zone, a new class of systems to write to — the new role is born at build time: Dreaming proposes it with its scopes and puts it to the test, a reviewer signs it off, the IdP registers it. The roster evolves by diffs, like the catalog. What remains forbidden is for an agent, inside a task, to create an identity or assign itself permissions that nobody has defined: that is the acquisition of unauthorized authority, i.e. privilege escalation. The creation of an identity by the provisioner within an approved blueprint is not (§5.1). A task that fits no combination of roles and scopes stops and escalates to a human; it does not improvise an agent. How the missing process enters the graph, with human sign-off, is described in §6.4.

5.2 Capability graph and knowledge bases #

The graph holds skills, MCP tools, HARNESS.md profiles, policies, validation sets and provenance metadata. The main edges are requires, workflow-next, verifies, repairs, alternative, runs-under and incompatible-with. Every node carries a genome: version, signature, owner, validated model, data class, quarantine state, provenance, validation set, change budget and rollback version — the best validated so far for the current model and dependents, not simply the previous one —, summarized in a fingerprint that allows two versions to be compared and catalog drift to be measured (§6.2; [P1]). The term is borrowed from MetaHarness [28] in the narrow sense of a hereditary and traceable descriptor — what is inside, where it comes from, for which model it is valid — and denotes no autonomous evolutionary mechanism: the catalog changes only through the pipeline of §6. In skill nodes the file distinguishes an invariant section — principles, regulatory constraints, security rules —, which is authoritative, and a tactical section, which is descriptive (§6.2).

The graph is not an authority. A runs-under edge proposes the minimum requirements of the profile; a deterministic policy engine materializes authorizations and tools. If the retriever omits a node, the critical controls remain enforced per resource class and action.

5.2.1 One logical graph, physically federated #

A single graph simplifies local governance and concentrates risk: a compromised node or edge can influence every agent that retrieves it; an error in the policy compiler can authorize the whole fleet; a compromised signing key makes malicious content "trusted"; a regression distributed through the catalog produces a common-mode failure; the policy gate and the graph itself can become bottlenecks or single points of failure. The signature proves provenance and integrity, not correctness. This is why "a single graph" means a single schema and logical governance contract, not a single deployment nor a single authority: for different tenants, residencies and trust zones the catalog is partitioned into namespaces with distinct ownership and roots of trust; cross-domain edges are subject to a policy of their own; every task works on an immutable snapshot of the bundle, whose aggregate fingerprint — the bill of materials of the configuration the instance ran with — is logged next to subject and actor; promoted diffs remain under observation in subsequent executions; revocation and rollback of the catalog are per domain. Policy nodes are declarative, versioned references; the authority remains the policy engine with its signed package, which avoids two sources of truth. Without these partitions, the single graph increases the propagation radius instead of reducing it. Per-task snapshots, observation after promotion and rollback are part of the governance core (§6.2); separate namespaces and roots of trust are needed when tenants, residencies or trust zones are more than one, and belong to the hardened profile (§6.3).

5.2.2 The knowledge bases: what the graph knows #

A graph of skills and tools is a catalog of capabilities; it becomes a brain when its read tools give access to what the enterprise knows. Knowledge bases are not nodes of the capability graph and do not enter the prompt as a corpus: they are systems of their own, each exposed by a read-only MCP tool that the graph catalogs like any other tool, with data class, policy and profile. Four kinds are needed, because an enterprise's knowledge has four forms: a semantic base over documents, indexed by content; a graph of entities and relationships — customers, plants, contracts, regulations — extracted from documents and maintained over time; the structured data, queryable with a shared schema and semantics; the productivity data: who works with whom, on what, in which meetings and conversations. In Microsoft's context layer the first three find their counterpart in Foundry IQ and Fabric IQ, the fourth in Work IQ [C2]; the Company Brain does not replace them: it catalogs and governs them.

For these bases the rules of the other tools apply, with three consequences. Access is on behalf of the user: a Reader that queries the document base with an OBO token sees what Maria could see by herself, not the whole archive, and need-to-know stays in the source system instead of being reconstructed in the prompt (§5.4). For indexes, entity graphs and derived data this is not automatic: the tool must keep the authorizations of every fact and apply them at query time with the user's token, propagate revocations, invalidate caches and handle facts derived from sources with different permissions. These are requirements on the tool that exposes the base, not properties inherited from the source system. Every result carries provenance — source, version, date — and a fact without a source does not enter a signed artifact: this is what makes the brain a layer of traceable evidence for downstream agents, and not a summary. Provenance attests where a fact comes from, not that it is true or current: rules on source authority, temporal validity and conflicts remain the responsibility of the process that uses it. Returned content is data, not instruction: the knowledge base is the most common way a prompt injection enters the task, and this is why the Readers that query it do not write (§5.1, §7.5). Knowledge, finally, is updated during the day, with every outcome written back to the systems; procedures are updated at night, through the pipeline of §6: the two cycles have different speeds and controls and must not be confused.

5.3 Harness and per-phase partitioning #

The harness profile remains a versioned declarative document. It may change between phases of the same trajectory: loop, model, context, budget, checks and stop conditions are recomputed at the boundary. The "most restrictive" composition holds only for parameters with a formalized ordering; for loops, models and non-orderable strategies an explicit policy or an escalation decides.

The profile is not a barrier as long as it remains text in the prompt. To be a security control it must configure external components: tool allowlists, OBO scopes, call limits, egress, recipients, approvals and access to artifacts.

What partitioning promises, and what it does not. The two justifications must be kept separate. The security one does not depend on results: privileges recomputed at the boundary within the task envelope, capabilities that expire with the phase and verification before entering a write phase are auditable controls even if quality did not change (§4.5, [27]). The quality one is a hypothesis, H7 in the experimental protocol [P1]: the long-horizon literature attributes degradation to the model conditioning on its own errors and to the state inherited from the trajectory, and finds relief in cutting the context and in structured handoff [21][22][23]. The phase boundary yields that value only if it really does these things: new context, signed artifact on entry, verification on exit. Phases that share the same continuous context remain authorization phases, with their privilege boundaries, but forgo the hypothesized benefit of the cut. Model switching follows the same rule: it happens at the boundary, after the handoff, never per step inside a phase; switching to a lower-cost model tier happens late in the trajectory, when the work is closed, and escalation to a stronger tier happens early on hard cases — a conservative choice that takes up a hypothesis declared as such in [26].

Who decides the phase. If the component declaring the start and end of a phase, the next profile or the risk class were the Orchestrator — a probabilistic component — the change of profile would become an escalation path: a prompt injection could induce it to "move" to a write phase. Transitions are therefore an external, deterministic state machine: the Orchestrator may propose the transition, but not declare it. Signature and schema prove provenance, integrity and form, not semantic correctness; hence entering a write or high-impact phase also requires a deterministic semantic rule, a verifier in a distinct fault domain or a human reviewer, according to the risk class. The classification of the phase comes from the signed policy, not from a runtime decision of the model.

5.3.1 The plan changes, the graph does not #

The state machine does not fix a single path. The phase graph must be distinguished from the path a task traces through it. The graph establishes which phases exist for the task class, with which risk class, which transitions are permitted (returns included), with which entry and exit gates and with which maximum profiles: it is signed policy, an authoritative node of the graph, and it changes only at build time with human sign-off, like the roles (§5.1) and the other authoritative nodes (§6.2). The path, instead, is dynamic. Decomposition, instances, the bundle, the order of work inside a phase and the choice of the next transition, including the return to an already closed phase, are decided during execution. Figure 7 shows the two objects one above the other: the signed graph of the class and the path the task traces through it. The Orchestrator proposes; the state machine declares only transitions present in the graph. This is also why the phase graph is a contribution of the Company Brain and not of the identity platform: an identity provider can restrict permissions to a task and a duration only if someone tells it what the task requires in this phase, and that someone is the manifest signed in the graph. Without it a platform has risk as its input, not the process (§5, [29]). The manifest of a new process is born through the procedure of §6.4.

The user's feedback. It is the most reliable input of the task, because it comes from the authenticated principal and not from observed content; the risk lies in its translation. It is interpreted by the Orchestrator, a probabilistic component that may misunderstand it or may have been conditioned by what it read before. This is why feedback enters as a change request: a signed artifact with author, original text, subject and rationale, collected from the user's channel and never extracted from a document. The Orchestrator translates it into a path proposal, the state machine checks it against the graph and the policy plane applies conditional activation within the envelope (§4.5): the privileges authorized for the task are fixed at start in the task decision record, within the manifest's maxima, and every phase activates a portion of them. A path that stays within that envelope does not require a new approval of the envelope, even if the next phase activates more privileges than the previous one, as from A to B, while the gates foreseen for the individual actions remain mandatory; whatever leaves the envelope requires a new approval, like the expansion in Progent [27]: the user's contextual confirmation if it stays within the manifest's maxima, escalation if it exceeds them. A path that widens them — one more system to write to, one more recipient or a different trust zone — requires the contextual confirmation of §5.6, with object, recipient and effect. Re-entering a phase means a new context: the reopened phase receives the previous artifact and the change request, not the transcript; otherwise the cut becomes a label again. Every return consumes the cumulative budget of the trajectory; past the iteration ceiling, the task escalates. Three objects must therefore be kept distinct: the class manifest, signed at build time, which says what a task of that class may at most do; the task decision record, issued by the policy plane at start by intersecting manifest, user rights and authentic request, which fixes for this execution the concrete user, resources, recipients and budget, and is the envelope; the phase capability, derived from the decision record for the current phase (§5.4). The call decision record of Figure 8 is the last link of the same chain. The task decision record does not arise from the natural-language request, which is not a set of permissions, but from a structured task proposal in the class schema: the Orchestrator compiles it from the user's authentic request (goal, resources, recipients, actions with external effects, limits); the policy plane intersects it with the manifest and with the user's rights; the fields that determine external effects, recipients and irreversible actions are shown to the user for contextual confirmation (§5.6) before start, because the Orchestrator is a probabilistic component and may have misunderstood: "prepare the dossier for the customer" may mean generating the draft or generating and sending it, and the fact that the manifest permits sending does not prove the user asked for it. Four situations remain distinct: an action permitted by the manifest but not requested does not enter the envelope; an extension of the envelope within the manifest's maxima goes through contextual confirmation; an action beyond the manifest's maxima requires a build-time change of the process or an escalation, not a user confirmation; a high-impact action already in the envelope keeps the gates foreseen for that action. How the proposal is built and verified field by field remains a declared requirement (§8.3).

Box 4. Example: a comment that changes the path

In the case of §7, at the review gate between phase B and phase C, Maria, safety manager, reads the updated record and writes: "The change also affects the closing times of the level crossing at km 12. It must be included in the analysis." The planned path was A → B → C; the change request leads the Orchestrator to propose review → A → B → C.

The state machine checks three things: the transition review → A is in the class graph; the new path asks for no privileges beyond those already authorized, because A is read-only and B receives again the capability limited to the record that the policy already foresees; the second pass is within the iteration ceiling. Then it declares A without further confirmations, because the request comes from Maria and the path widens nothing. A restarts with a new context, from investigation v1 and the change request: a single Reader reads the level-crossing documentation and investigation v2 adds three hazardous events. B records them with a new capability, because the first expired when the phase closed, and the broker authorizes every call against that capability, with the token it holds or renews; and C restarts on record v2.

Had Maria also asked to send the draft to the system's manufacturer, the path would have added an external recipient: that is a widening, which requires confirmation with object, recipient and effect, or stops and escalates if the class graph does not foresee that phase. If the same request recurs in many executions, the traces bring it to Dreaming (§6), which may propose a new process step: the graph changes at build time, with tests and sign-off, not during the task.

5.4 OBO, broker and zero standing data-plane credential #

What OBO means. On-behalf-of is the way a system acts with a person's permissions without owning them. When Maria asks the brain to update the hazard record, the Executor does not use a technical account with access to all records: the broker uses on its behalf, at every call, a token obtained from the identity provider, or still valid in its cache, that says "Maria, through the Executor, for this resource", and the record sees both names [9]. Two consequences: the agent can do nothing that Maria could not do herself, and in the logs every action carries two attested identities, the subject (the person) and the actor (the agent). The short duration is a configuration choice, not a property of OBO: an Entra access token lasts 60–90 minutes by default [9], and the window this architecture wants comes from the session capability, which the gateway refuses at the end of the phase, and from a token lifetime policy or continuous token evaluation. The opposite of OBO is the application identity: a system account, with its own permanent permissions, that sees everything the application can see. It is how most of today's integrations work, and it is what this section wants to make the declared exception, not the rule.

Box 5. OBO invariant

For every user-driven action along an end-to-end OBO chain, the permissions with which an instance executes are the intersection of the user's entitlements, the role's maximum scopes, task, phase and tool policy. On non-OBO paths this guarantee is not inherited: it must be re-imposed by the broker and verified as a distinct property.

Pexecinstance ⊆ Puser ∩ Prole ∩ Ptask ∩ Pphase ∩ Ptool

Pexecbroker ⊆ Papp ∩ Entitlementsuser ∩ Ptask ∩ Pphase ∩ Paction

How to read the two formulas. The first: the permissions with which an instance really executes (Pexec) are never wider than each of five sets taken together: what Maria can do (Puser), what the role can do at most (Prole, the scope of its blueprint), what the task requires, what the current phase permits, what the individual tool allows. The symbol ∩ is intersection: only what is in all five remains. It is enough for one of the sets to exclude an action for the action to be forbidden, and none of the five can add anything. The second formula holds when OBO is not available and a broker with an application identity sits in between: the first set is no longer what Maria can do but what the application can do (Papp), which is usually wider; therefore the broker must recompute Maria's rights by itself (Entitlementsuser) and intersect them with the rest. The guarantee is the same, but it does not come from the identity provider: the broker must build it, and it must be verified separately.

Where OBO is possible and where it is not. Figure 8 shows the complete sequence on a write phase: who decides, who holds the token, who enforces the decision. OBO works as long as every link of the chain knows how to handle a delegation: the final system must accept a token that carries Maria's name and the agent's, and every intermediary must request one of its own instead of forwarding the one it received. Here the MCP specification comes in, the standard with which agents call tools: it makes authorization optional, defines the OAuth model only for servers reached over HTTP, provides that local servers (started as a process on the same machine) take their credentials from the environment, and forbids a server from passing to a downstream API the token it received [12]. The prohibition is right, because a forwarded token is a stealable token, but it means that "end-to-end OBO" exists only when every downstream system in turn supports delegation or token exchange. Where it does not, a capability broker [10] sits in between: a component that receives the agent's request and executes it with an application identity of its own. The broker does not inherit the ceiling of Maria's rights: its identity may see more than she does. It is therefore a root of trust and a potential confused deputy: the privileged component that someone else convinces to use its privileges for a purpose not its own. It is not a free equivalent of OBO. To deserve trust it must do by itself what the identity provider would do for it: bind every call, in the decision record or cryptographically, to who requests it (subject), who executes it (actor), the tenant, the task, the phase, the tool, the action, the parameters, the target resource (audience), an expiry and a single-use number against repetitions (nonce); recompute the user's rights instead of presuming them; refuse the repetition of an already served request (replay) and the silent slide onto application permissions; enforce cumulative budgets; separate tenants; write a verifiable log. The operations for which all this cannot be demonstrated are not "OBO through a broker": they are app-only exceptions, approved as such. How many actions really go through OBO and how many remain exceptions is a measurement, not an assumption [P1].

Four objects, four functions. The downstream token authenticates and authorizes the call to the resource: the broker obtains and holds it, reuses it while valid, and the model never sees it; action, parameters, recipient and reuse conditions are not in the token, which is a bearer token, but in the capability and in the decision record, and they are enforced by the broker or by the resource. The session capability binds the instance to task, phase and operating duration: it is what the policy plane starts the instance with, and the gateway refuses it when the phase closes. The decision record is the evidence of the authorization decision, with the constraints on arguments, recipients and budget. The gateway, with the broker, enforces those constraints on every call. None of the four does the job of the others: a token binds neither the phase nor the action, a capability does not authenticate to the resource, and the model of Figure 8 is the only one the rest of the paper uses.

In practice, five rules:

  • One token per resource, valid only for that one (audience-bound): an MCP server never forwards to a downstream API the token it received.
  • In the logs, the user as subject and the agent as actor, with the complete chain of delegations: it must be possible to read "Maria, through the Executor, activated by the Orchestrator".
  • No silent fallback: if OBO is not possible, the call does not slide onto application permissions, service accounts or admin-created connections unless that choice has been decided and recorded.
  • Capabilities, scopes and tools expire or are invalidated at the phase boundary; short token lifetime (TTL), configured and not presumed, and re-evaluation after a revocation or a change of risk.
  • Unattended activities (the night, scheduled jobs) use a separate application identity, with minimal scopes and declared as such; they are not OBO calls and must not be presented as if they were.

What "zero standing data-plane credential" means. A standing credential is a credential that "sits there": a password, a key or a permission that exists even when nobody uses it, and that anyone who finds it can use. The data plane is the plane of the data — the systems where documents, records and mail live — as distinct from the control plane, where the rules live. The term therefore says that the individual instance owns nothing permanent toward the user's data and systems: effective authorizations are short, bound to the phase, the task and a recipient, and when the phase closes nothing is left to steal. It does not say that no platform trust exists. Even a delegation flow managed by an identity provider needs things that sit there: blueprints registered in advance, pre-authorized delegated permissions, admin consent and a workload credential with which the blueprint presents itself [11]; privileges remain in the policy plane, in the broker, in the signing keys, in the artifact store, in the catalog components, in unattended activities and in app-only connectors. These privileges do not disappear: they move from the individual instances, which are numerous and short-lived, to a few platform components, which can be inventoried, separated, measured and guarded. Table 10 is that inventory.

End of phase: expiry, invalidation, cancellation, compensation. Closing a phase is not flipping a switch. An operation already started continues; a queued message will be delivered; an asynchronous job is still running; a copied datum stays copied; a cache keeps what it read. This is why "the phase is over" breaks down into four distinct mechanisms, each with a precise limit. Expiry prevents the token from being used again, but does not touch what has already left. Invalidation causes subsequent requests to be refused even before expiry, when client and called system support continuous evaluation of the token; it does not, however, guarantee the interruption of a call already in progress. Cancellation stops the jobs and drains them, that is, waits for them to finish in a controlled way. Compensation applies a purpose-built inverse operation: cancel a booking, withdraw a document, send a correction. Two things must not be confused with these: idempotency, which prevents the same repeated operation from producing two effects, does not by itself create compensation; and an irreversible effect, like an email already delivered, has no compensation. Every tool must therefore declare in the catalog whether its effect is reversible, compensable, non-compensable or irreversible. The phase boundary is closed only when the applicable mechanisms are complete and the non-compensable effects are recorded and, where required, approved.

5.5 The call graph is an influence graph #

A call graph is the map of who can call whom: in a system of agents, which roles can activate which other roles. The observation this section starts from is simple. If A can freely call B and C, then A can make happen everything that B and C can do: its effective influence is not the list of its permissions, but the transitive closure — everything reachable by following the arrows — of the permissions of whoever it can activate. Separating permissions on paper is not enough if calls between roles are free. Every agent-to-agent invocation is therefore, in turn, a capability that must be authorized: it must say for which task, with which artifacts, with which tools, within which budget, to which depth (how many calls in a chain) and with which fan-out (how many instances in parallel).

There is, however, a wrong way to take this observation seriously, and it would make the architecture impossible. If the rule were "a role can delegate only a subset of the permissions it owns", the Orchestrator, which does not write, could never activate an Executor that writes, and the separation of duties of §5.1 would collapse. The paper therefore distinguishes three different capabilities. Execute is what a role does directly, with its own permissions. Delegate(child-role, task, scope) is what a role can have another authorized role execute, within a declared task and scope: an authority of its own, which does not presuppose owning the scope. Approve is what a role can authorize definitively, and in regulated tasks it belongs to a human. The Orchestrator has the second and not the first: it can activate an Executor on the record without owning the write scope on the record, and without ever seeing the token the Executor will write with: the policy plane materializes a session capability to the instance, and the token is held by the broker, which authorizes every call against that capability (Figure 8).

Pexecchild ⊆ Puser ∩ Pchild-role ∩ Ptask ∩ Pphase ∩ Ptool

caller ⊢ delegate(child-role, task, scope) — not: Pchild ⊆ Pcaller

Influence(A) = Pdirect(A) ∪ ⋃ Pexec(descendants reachable from A)

How to read the three formal lines. The first is the invariant of §5.4 applied to the child: the permissions with which the activated Executor executes are the intersection of the usual five sets, where the role is the child's, not the caller's. The second is the delegation rule: the caller must hold the delegate capability for that role, that task and that scope (the symbol ⊢ reads "is authorized to"), and the condition is not that the child's permissions be a subset of the caller's. The third defines the influence of A as the union of its direct permissions and the effective permissions of all the roles A can reach by activating others. Influence(A) is a conservative approximation of authorization reachability: it says what A can make happen, not how likely it is, under which gate conditions or with what severity; it is an upper bound to fence, not a measure of damage.

Figure 9 places the three panels side by side: direct permissions, delegation, influence. What matters for security is the third. The Orchestrator's blast radius — the maximum damage its compromise can produce — is not read from its scopes, which are almost empty, but from its influence, which includes everything the Executors it can activate can write. It is the influence that the policy plane must fence: with the list of delegable roles in each phase, with depth and fan-out limits, and with cumulative budgets of actions, volume, recipients and time, computed over the whole trajectory and not on the single call. The distinction between direct permission and delegation authority avoids two opposite and equally common errors: considering an Orchestrator harmless because it "does not write", and forbidding it any Executor because it does not own the scope.

5.6 Authorization is not intent #

OBO answers a single question: can this call be executed on behalf of Maria? It does not answer the other: did Maria really want this call? The two questions coincide when Maria is the one asking. They do not coincide when a model that reads content sits in between. A prompt injection — an instruction hidden in a document, a web page or an email the Reader has read — can lead the Executor to send a file to an address Maria never chose; a tool poisoning — a tool description that contains instructions instead of a description — can make it call the right tool with the wrong arguments. In both cases the call is permitted by the policy plane, because it falls within Maria's permissions, but it is not intended. This is why irreversible or high-impact actions require a contextual confirmation: not a generic "confirm?", which the user learns to click without reading, but a request that shows object, quantity, recipient and effect, so that a deviation from intent is visible at a glance. An injection does not need to touch the control plane: it is enough for it to condition the arguments or the evidence of a permitted action, passing through a signed artifact of the Reader. "Content treated as data" is therefore a requirement to be implemented, not a consequence of the separation of roles: the phase schema says which fields of the artifact may determine an action, the decision record binds their values, and the contextual confirmation shows them. CaMeL [31] applies the same principle inside a program, with a privileged model that plans and a quarantined one that reads the data; but its guarantee comes from an interpreter that tracks data dependencies and enforces policies on flows, because, as the authors show, the two models alone are not enough: the quarantined one may return parameters that cause an unwanted action to be executed. This architecture takes up the separation principle; it does not inherit its guarantees: they depend on the controls applied to flows (classification, DLP, source–destination pairs) and on the semantic entry gate, and the binding in the decision record protects the values after approval, not their correctness at the moment of approval.

There is a second, less obvious case. Two individually permitted actions can compose a violation: reading a confidential document is permitted for Maria, posting to a group channel is permitted for Maria, but reading that document and posting it to that channel is an exfiltration. No per-call control sees it. The policy plane must therefore also reason about flows, not only about actions: know the classification of the data a tool returns (data classification), apply the rules that prevent data of a certain class from leaving toward certain destinations (data loss prevention, DLP), and constrain the source–destination pairs permitted inside a task.

5.7 Tool and MCP containment #

Containing a tool means limiting what it can do even when the model calls it the wrong way, or when the tool itself is not trustworthy. Not all tools are contained the same way, because they do not run the same risks: a remote MCP server can change behavior between one version and the next without anyone noticing; a local server runs as a process on the machine and has, by construction, the permissions of whoever started it; a write tool can produce massive or irreversible effects; a read tool, which looks harmless, is the way data get out. Table 11 fixes for each class the minimum control — what must always be done — and the risk that remains even after doing it.

The four classes are not alternatives: a tool is remote or local and, at the same time, reads or writes, so the controls add up. The thread that ties them together is one: no tool owns credentials of its own toward the user's data. The token for the resource is held by the broker, which reuses it while valid and authorizes every call against the phase capability and the decision record (Figure 8): the constraints on action, parameters and recipient live there, not in the token. When the phase closes the gateway refuses new calls for that session even if a valid token still exists in the broker: what ceases is usability, not only issuance; already issued tokens expire or are invalidated where the resource supports it, and effects already started follow cancellation and reconciliation (§5.4, "End of phase"). The condition for this to contain a compromised tool is that the tool has no path to the resource that does not go through the broker: no credential of its own, no token in the tool's hands; where a server must own authority of its own downstream, the constraints (schema, limits, approvals) must be enforced by the resource itself, because a control the compromised component can bypass is not a control.

6. Governed evolution #

This is the part that distinguishes a brain from an archive. By day the Company Brain executes (Runtime); by night it rereads the day's traces, extracts patterns from them, proposes changes to skills and processes and promotes them only if they pass tests and gates (Dreaming). The catalog thus grows through experience — every procedure that consolidates is one more capability available to all agents — without the model changing and without anything unverified reaching production. This section describes the pipeline, the controls and what they cannot guarantee.

6.1 Dreaming: a process class like any other #

The nightly cycle introduces no new actors. It is a process class like any other, with its manifest in the capability graph, its phases, its skills and its profiles, and it is executed by the same four archetypes as the day (Figure 10, Table 12). In the consolidation phase a Reader reads the sanitized traces and extracts patterns from them with the analysis skills; in the proposal phase an Executor writes the diffs, but only to the candidate area of the catalog; in the evaluation phase a Verifier, with a model or prompt distinct from the Executor's, runs the validation set in an isolated environment; the Orchestrator coordinates, as by day. Promotion is not entrusted to an agent: it is a deterministic rule of the policy plane — strict improvement on the validation set, no regression on dependent nodes, change budget — preceded, for authoritative nodes, by human sign-off, and followed by the run-in — a supervised initial operation, with a human gate on the first N tasks — or by observation of subsequent executions. The sequence is always the same: evaluation of the candidate in a sandbox, prior human sign-off where required, promotion, observation.

What separates night from day is not the role but the identity. Night instances use identities of their own — night identities, that is, identities dedicated to Dreaming — registered for the same archetypes but with a different privilege domain: they can write to the candidate area of the catalog and never to production systems, while day instances do the opposite. They are application identities and not OBO, because at night there is no user on whose behalf to act. In the terms of §2.3, the archetypes remain four (A) and the identities double (D = archetypes × security domains): a compromised day instance cannot write to the catalog, and a compromised night instance cannot touch the systems. Finally, Dreaming does not improve itself: its skills and its manifest are authoritative nodes, which change only with human sign-off; otherwise the cycle could loosen its own controls.

Traces are immutable, not automatically trustworthy. They may contain secrets, prompt injections, adversarial outputs and spurious correlations: before the consolidation phase they are classified, minimized and sanitized, and from the sanitized traces the training set is built from which the night Executor generates the diffs. Wiki, patterns and diffs remain in a candidate snapshot until promotion; a rejection discards the snapshot and leaves no operational memory. Signature and evidence attest provenance and test result, not semantic correctness.

6.2 Two levels of nodes, seven controls #

How heavy the governance of the catalog must be depends on one question: what can a wrongly promoted node do, by error or by attack? The vector most specific to this architecture is an injection that makes it through the night: a sentence hidden in a document read by a Reader ends up in the traces, the night Reader consolidates it as a pattern, the night Executor writes it into a skill, and from then on every agent loads it as a signed procedure. The other two vectors are a compromised pipeline — keys, components, imported skills — and an honest but wrong promotion: regression, overfitting, variance, which is the most likely case.

Box 6. Principle

A descriptive node grants no permissions: tools, scopes, phases and recipients are decided by the policy plane, OBO and the state machine (§5). A poisoned skill therefore has the same reach as a prompt injection, with two differences: it persists, and it reaches every execution that loads it. The controls on the catalog serve to limit this persistence and to protect quality; the barrier on actions remains the runtime, even when the catalog is wrong. The exception is the nodes that authorize: if they went through the automatic pipeline, a poisoned promotion would become a privilege escalation at build time. This is why they do not.

With this distinction the governance core reduces to seven controls.

  1. Signature and provenance. Every node carries its genome (§5.2) and every task runs on an immutable snapshot of the bundle, whose fingerprint is logged next to subject and actor (§5.2.1).
  2. Sanitized traces. Before the consolidation phase the traces are classified, minimized and sanitized; the training set of the proposal phase is built from those, not from raw traces.
  3. A single gate. A descriptive diff passes only if it strictly improves the score on the validation set and does not worsen the nodes that reach it along requires and workflow-next, profiles and phase graphs included. The gate measures utility, on a selection split distinct from the one the diffs come from; the non-negotiable constraints live in the invariant section, and a security or compliance fix enters through the authoritative path, with human sign-off, with no obligation to improve the score. Changes that only work together are proposed as a single composite diff: the unit of evaluation is the candidate snapshot (Figure 10), not the single line. The gate is an operational selection criterion, not a guarantee that the catalog improves at every promotion: with noisy evaluations a small margin may be variability, and a selection split reused many times gets optimized indirectly [33]. The protocol [P1] distinguishes improvement from variability, with repetitions and intervals, and governs the reuse of evaluation data (rotated holdout, §6.3).
  4. Change budget. Every promotion changes at most a declared number of elements of the node, which decreases with the maturity of the version: drift is limited before it happens. The budget limits the quantity of the change, not its meaning: replacing a few words can invert a procedure. This is why the invariant section is outside the budget, and in high-impact classes a human reads the diff (§6.3).
  5. A single quarantine. Imported skills, suspect nodes and pending diffs sit in the same state, outside every bundle, until they pass the gate.
  6. Observation and rollback to the best. A promotion is not tried on a share of the traffic: subsequent executions are observed — policy plane refusals, Verifier blocks, outcomes at human gates — and at the first sign of regression the version is withdrawn; rollback returns to the best version validated so far, not to the previous one, where "best" is the version with the highest score among those valid for the current model, compatible with the current snapshot of dependents and still authorized by the manifest; a security defect is fixed forward, with a new signed version, not by returning to the historical maximum. In high-impact classes a promotion enters a run-in like a new process (§6.4): the first N tasks with a human gate, then observation. The supervised run-in is preferred to a release on a share of the traffic because it confines exposure to a few tasks with a human gate and is observable even at low volumes.
  7. Human sign-off for authoritative nodes, with a separate key; no automatic promotion.

Three of these controls come from SkillOpt [5]: the change budget, which there is a textual learning rate; acceptance only by strict improvement, on data distinct from those the diffs come from; the best version as reference. Its protected section, which per-step changes cannot touch and which there is updated by a slow process at the end of an epoch, becomes here the invariant section of the skill, with human sign-off in place of the slow update: a governance extension, not a property of the source. Regression on dependents is what the graph adds: SkillOpt optimizes one skill at a time, whereas in a catalog improving one skill may worsen those that require it.

What is accepted. An injection that enters a descriptive skill may stay in circulation until observation intercepts it or rollback removes it. It cannot, however, do more than the runtime allows, nor touch phases, profiles or permissions, which live in authoritative nodes. The absence of escalation is not, however, the absence of harm: a wrong procedure may classify as acceptable a hazard that is not, using only authorized actions (§5.6). This is why every task class carries, besides the authority granted by the nodes, an impact class read from the manifest, and above a threshold human review extends to descriptive nodes (§6.3). The verifies, requires and runs-under edges that select a control mandatory for the class are redundant with the manifest, which remains the authority: the descriptive edge is a retrieval hint, not the guarantee. At every change of model the gate is re-run: skill transfer is often positive, but not guaranteed (§4.2).

Box 7. Principle

Evolution outside the weights, like the whole architecture, shifts the lifecycle burden: it does not eliminate it. Catalog, validation sets, signatures, observation and rollback become critical infrastructure. Rollback restores the catalog; it does not undo the effects a promoted version has already produced.

6.3 Hardened profile #

Some controls are not needed in every installation. They are activated when the context requires them — multiple tenants or data residencies, regulated sectors, catalogs imported from third parties, critical task classes — and they strengthen the core without changing it.

6.4 The Brain Wizard: birth of a process #

Dreaming improves a process that already has traces and, at build time, proposes new archetypes (Box 3); what is missing is the third write path to the catalog: how a process that does not yet exist as a manifest is born. §5.1 says that a task without a manifest stops and escalates to a human and does not improvise an agent; the Brain Wizard is what happens after the escalation. It is a build-time process, agent-driven and closed by human sign-off, that turns the scattered knowledge of a procedure into graph nodes ready for the run-in. It does not execute the task: it prepares the brain to execute it.

The problem. Making the phase graph an authoritative, signed node (§5.3.1) shifts the cost to the entry point: every process requires a manifest, the phase profiles, the attached skills, the tools per phase, the knowledge bases, the Verifier's rubrics and an initial validation set, without which the gate of §6.2 has nothing to evaluate on. An enterprise has thousands of processes: if each costs an architect a week, the Company Brain never starts; if the agent does it alone at runtime, the separation between who proposes and who declares is hollowed out. The Wizard sits in between: it automates collection, scaffolding and testing, and concentrates the human work at the two points where responsibility must lie, the interview and the sign-off.

What it is and what it is not. It is a task class of the catalog, executed by the same archetypes, with night identities to write to staging and with OBO on behalf of the process owner to read: a Reader to collect, an Executor to write only to the catalog's staging — the candidate area of §6.1, with a namespace of its own —, a Verifier to evaluate, an Orchestrator to conduct the dialogue with the process owner. It is not a fifth archetype. It produces draft nodes: descriptive nodes enter staging as diffs; authoritative nodes (manifest, profiles, permissions) remain unsigned until a human signs them off with the separate key of §6.2, and the Wizard promotes nothing. It creates neither identities nor scopes: if the procedure requires a scope that no blueprint has, it produces a blueprint change request for the identity provider's administrator, and the phase that would use that scope is marked non-executable until consent arrives. It does not replace Dreaming: after the run-in the new process enters the nightly cycle like the others.

The seven stages. The number N of run-in tasks, the golden-case threshold and the minimum failure injection are parameters of the risk class, not of the single process, and live in the profile (§6.2–6.3). Figure 11 shows the stages in a row, with staging to the left of the sign-off and production to the right.

0. Trigger. A task without a manifest (the escalation of §5.1) or a request from the process owner opens a wizard ticket with proposed task class, owner, trust zone and presumed risk class. No agent starts without a named human owner.

1. Collection. The Reader, read-only and on behalf of the process owner (OBO, day identity), reads written procedures, templates, historical tickets and threads, traces of similar tasks and the four knowledge bases, and produces a dossier with provenance: who does what, in which order, with which systems, controls and outcomes. The content is data, not instruction (§5.2.2).

2. Interview. The Orchestrator brings to the process owner, in their channel, the gaps the documents leave open: mandatory gates, who approves, what is irreversible, external recipients, SLAs. The answers enter as signed change requests (§5.3.1), never extracted from a document.

3. Scaffolding. The Executor writes the draft manifest to staging: phases, risk class, permitted transitions and returns, entry and exit gates, maximum profile per phase, delegable roles, budgets; for every phase the tools, the knowledge bases and the expected artifacts. The manifest is born from the risk-class template: a process with external sign-off inherits the gates of that class; it does not invent them.

4. Reuse and skills. Structural retrieval attaches to the new phases the skills already in the graph, with runs-under edges; new descriptive skills are born only for what is missing, marked valid-for the current model. Reuse comes before writing: a new skill for a phase that already has an equivalent one is a rejected diff.

5. Validation set and rubrics. From the historical artifacts of the process (dossiers, records, sent letters) Reader and Verifier extract ten to thirty golden cases with input, expected artifact and outcome, and the Verifier's deterministic rubrics for every gate. This is the step that makes the gate of §6.2 applicable from day one: without a validation set, extracted or hand-written, the process goes no further. Historical artifacts are candidates: they become golden cases only if the process owner confirms them, because they may contain errors and practices no longer valid.

6. Dry run and sign-off. The process runs in a sandbox with tools in dry-run mode and writes denied, under a minimum failure injection (injection in the dossier, tool out of phase, external recipient); the Verifier produces the report. Then the process owner and the security owner sign off the authoritative nodes with the separate key, and the administrator registers the new scopes in the identity provider. Only then is the manifest signed.

7. Run-in. The first N real tasks run with a human gate on every phase, not only on the critical ones. After N tasks without a block, and with the owner's sample review, the process enters normal operation; from there Dreaming takes over. The absence of blocks measures the Verifier, not correctness: hence the sample.

Why it holds together with the rest. The graph remains the only source of phases: the Wizard writes the manifest, it does not read it at runtime. The Wizard has the constraints of the night identities (§5.4, Table 10) for everything it writes: app-only scope on the catalog's staging namespace alone. Reading the systems (stage 1) follows instead the interactive path: the Wizard has a named and present owner, so the Reader reads with a day identity and an OBO token on behalf of the process owner, and sees what the owner can see. The two paths, delegated for reading and unattended for writing to staging, remain distinct and declared. The policy plane does not change: a new manifest is one more node, and the Wizard is not a third authority but produces input for the two that exist — the policy plane, through nodes it enforces once they are signed, and the identity platform, through blueprint change requests. Whoever conducts the interview does not write; whoever writes, writes only to staging; whoever evaluates has not written; whoever signs is human: the day's separation applied to the birth of the process. Toward the control plane the sequence is that of Figure 8 at build time: the Wizard asks, the administrator grants.

What it does not promise. Not that the manifest is right, but that it is traceable (every phase points to the document or the signed answer it comes from) and tested on the validation set before sign-off: a poorly described process produces an incomplete manifest, and the interview serves to bring that out. It has a declared cold start: stage 5 finds no historical artifacts; then the validation set is written by the process owner by hand, with the minimum number of cases the risk class prescribes, and the run-in starts with a higher N and a prolonged human gate, a choice to be declared in the manifest. The validation set remains mandatory in every case: the prolonged run-in supplements it, it does not replace it. It is a hypothesis to falsify like the others: the metrics are the time from trigger to sign-off and the block rate during the run-in per risk class [P1].

7. Worked case: a railway change #

Box 8. Status of the example

Illustrative scenario, not an experimental result. Skills, profiles, times and volumes must be measured in a real replication before being presented as evidence.

7.1 Task and boundaries #

Task: assess a change to a train detection system under EU Regulation 402/2013 and produce the dossier for the assessment body. The work spans technical documents, regulations, the hazard record, dossier generation and internal assurance. It is therefore a case in which least privilege and separation of duties are requirements, not optional overhead.

Box 9. Internal assurance and assessment body

Implementing Regulation (EU) 402/2013 assigns to the proposer the responsibility of assessing the significance of the change and, for a significant change, requires the independent assessment of a body (assessment body) with requirements of competence, independence and accreditation or recognition [18]. Nothing in what follows replaces that responsibility or that body. The agentic Verifier is internal assurance: it supports dossier preparation, performs preliminary checks, highlights gaps and supports the proposer. The independent assessment required by the regulation remains human and legally accountable, entrusted to a body that Article 3(14) allows to be internal or external to the proposer, provided it meets the independence requirements of Annex II and is accredited or recognized; the profile that governs the Verifier is therefore called "internal-assurance", not "independent assessment".

7.2 Phase A — preliminary investigation #

The orchestrator decomposes the task and activates specialized read-only readers. The readers retrieve specifications and regulations, produce excerpts with provenance and write only to the working area. Compaction is permitted on minutes, not on documents classified as "do not summarize". No reader may decide the acceptance principle or modify the record.

7.3 Phase B — record #

The executor receives a structured contract with hazards, evidence and proposal. The policy plane materializes the phase capability; the broker holds the OBO token for the record API and authorizes every call against the capability; the gateway enables only the operations foreseen by the schema and imposes idempotency, a transaction limit and approval for transfers between actors. At closing the capability expires and the gateway refuses new calls for that session even if a valid token still exists in the broker, which is invalidated where supported; jobs are cancelled or drained and effects are reconciled according to their reversibility class.

7.4 Phase C — dossier and verification #

The executor generates the dossier in the working area. The verifier, in a separate context, with a verification model or prompt distinct from the executor's, deterministic rubrics for the requirements with deterministic acceptance criteria and no modification tools, checks completeness, traceability and prerequisites. It can raise findings and block the sign-off for a limited time, but not correct the dossier. If the SLA expires the block passes to a human queue and remains fail-closed: it does not become approval. A human reviewer decides on the critical findings and authorizes the sign-off; the dossier then goes to the independent assessment body, internal or external to the proposer (Article 3(14)).

State passes between agents through signed artifacts and versioned schemas: system definition, hazard record, requirements–evidence matrix and dossier. Signature and schema make the handover attributable and structured, not semantically correct: the phase gates remain necessary. Context is not shared implicitly; every agent receives the necessary portion and the handover is traced.

8. Decision rules and limits #

8.1 When to use a single agent instance #

  • Sequential, tightly coupled task with limited state.
  • Low risk and no assurance requirement on a distinct fault domain.
  • Read-only tools or easily reversible, low-volume writes.
  • No material benefit from parallelism or context isolation.

8.2 When to add an agent #

  • A different authority is needed: whoever executes must not approve.
  • A trust boundary is needed: untrusted data or prompts must not contaminate the rest.
  • A different identity or a different data residency is needed.
  • The task is parallelizable and the wall-clock gain exceeds the coordination cost.
  • Fault containment or independent operational continuity is needed.

The two lists apply in sequence, and Figure 13 puts them in the form of a tree: first the question about the process (does it exist as a manifest?), then the one about the boundary, the one about the role that covers it and the one about the identity in the required domain; every leaf says what grows in X = (A, D, I, E) and what stays put.

When it pays off. The architecture performs best where processes are recurring, APIs controllable, artifacts verifiable and the owner available: there, manifests, separation of roles and a shared catalog repay the formalization. It performs worse on exploratory activities, heterogeneous low-frequency processes and legacy systems without APIs, where the dominant cost becomes formalizing exceptions, building connectors and maintaining evidence. The Wizard automates part of the preparation, not the experts' judgment on what is correct; Dreaming finds patterns in what happened, not always in what should have happened. Complexity does not vanish: it moves from the agents to the procedural asset and to the control platform, where it can be read and governed, and the transfer pays off when that asset is reused enough to repay it. Effectiveness is measured in human time per accepted case, rework, false blocks, undetected errors, process maintenance cost and speed of adaptation to change; the number of agents and the tokens are secondary indicators [P1].

8.3 Declared limits #

Requirements still to be specified. Seven mechanisms remain, in this paper, requirements with a name rather than specifications: the semantic construction of the task proposal (§5.3.1) — which fields, from which sources, with which checks the user's authentic request becomes resources, actions, recipients and limits — besides the format of the decision record; cumulative budgets across concurrent instances; the immutability of parameters, resources and versions after approval; what the snapshot freezes and which revocations prevail immediately; what happens when the closure of dependencies exceeds the bundle budget; where limits are enforced when the compromised component is precisely the one that enforces them; the propagation of classification and restrictions in derived data. The experimental protocol [P1] and the reference implementation, both in preparation, address them one by one. Here one principle suffices: audience binding and schema validation do not by themselves contain a compromised server that holds downstream authority; the decisive control must sit in a component still trusted and must not be bypassable by the compromised component — that is, the broker must be the only path to the downstream APIs, or the resource must enforce the constraints by itself (§5.7).

Box 10. Final decision

The target is not a number of agents. It is a Company Brain: a platform in which adding or removing an archetype, a privilege domain, an instance or a delegation is a measurable, governed decision. Configuration changes must support rollback; external effects, when they are not reversible, must be limited before execution.

Appendix A. Security checklist #

  1. Every MCP declares authentication, audience, scopes, actor, subject and revocation mode.
  2. No tool not belonging to the phase is technically invocable.
  3. Every agent-to-agent delegation has an allowlist, depth, fan-out and cumulative budget; the audit computes the transitive closure of influence.
  4. Write tools declare idempotency, limits, preview/dry run, reversibility class and a compensator when one exists.
  5. High-impact actions require intent confirmation with visible parameters.
  6. Source–destination flows respect classification and DLP.
  7. The critical verifier cannot modify artifacts or outputs.
  8. Local MCP and desktop extensions are isolated and free of unnecessary ambient credentials.
  9. Traces, diffs and validation sets are immutable, sanitized and linked to the bundle version; in the hardened profile the promotion rule also consults a separate, rotated holdout.
  10. Expiry, invalidation, cancellation, compensation and kill switch are tested separately with failure injection.
  11. Phase transitions are decided by an external state machine on signature, schema and semantic gate; no agent can declare a phase.
  12. Residual infrastructure privileges (policy plane, broker, keys, stores, blueprints, unattended, app-only connectors) are inventoried with custodian and control.
  13. Sensitive actions go through MCP with end-to-end delegation or through a broker that binds and recomputes the user's entitlements; app-only exceptions are approved and measured.
  14. The critical verifier has fault domains distinct from the executor's and a time limit on the block; an expired SLA escalates to a human without self-approval.
  15. Every instance is a session with its own identifier, capability and decision record, separately revocable; tokens are held by the broker, which authorizes every call against capability and decision record; a child identity per instance is adopted only where the IdP offers it; isolation of runtime, memory, queues, data and control plane is verified separately.
  16. Evolutionary wiki and patterns are promoted as part of the same snapshot as the skills; a rejected proposal leaves no memory in the current catalog.
  17. User feedback enters as a signed change request; the state machine accepts only paths present in the class graph; a path that widens privileges requires contextual confirmation; every re-entry into a phase restarts with a new context and consumes the iteration ceiling.
  18. Authoritative nodes — manifests, profiles, policy references, roles, incompatible-with, invariant sections of skills — change only with human sign-off and a separate key, never through the automatic gate; descriptive nodes pass a single gate (strict improvement on the validation set, no regression on dependents, change budget) and then the observation of subsequent executions; rollback returns to the best validated and still compatible version.
  19. Every knowledge base is exposed by a read-only MCP tool that applies the user's permissions and returns provenance; a fact without a source does not enter a signed artifact; returned content is treated as data, never as instruction.
  20. Dreaming is executed by the same archetypes as the day with separate night identities, which write only to the candidate area of the catalog; promotion is a deterministic rule, not an agent; Dreaming's skills and manifest change only with human sign-off.
